# DeepSeek 缓存命中分析与改进方案

实施进度：2026-10-15第一阶段已实现并验收，待生产发布；第二、三阶段依赖自然任务基线，尚未开启。详见 [实现与验收记录](cache-observability.md)。下文费用数据与研究结论保留原分析口径。

分析日期：2026-10-15。依据用户提供的两批 CSV、当天读取的 DeepSeek 官方文档及 Pi 官方文档，并对照工作区 `a45af8b`（功能版本 `4a652fe`）的实现。本轮只做分析和方案，未修改应用代码、模型参数、预算或生产配置，也未发起收费模型测试。

## 结论

这组调用已经大量使用原生输入缓存：总体命中率 60.16%，15日样本为 64.21%。优先改善实际请求前缀和任务调度，再完善有效结果复用；不建议为缓存专门迁移 Responses API、添加 sessionId 或降低思考强度。

总费用中 72.41% 来自输出。缓存优化能降低输入费用，但输出长度和重复付费调用更直接影响总成本。继续采用用户此前指定的顺序：先约束输入提示词中的输出要求，只有真实质量与费用样本证明必要时才降低思考强度。

## 2. 官方机制与本站实现

### DeepSeek 原生输入缓存

[官方上下文硬盘缓存文档](https://api-docs.deepseek.com/zh-cn/guides/kv_cache)当前说明：缓存默认开启；命中要求完整匹配已经落盘的缓存前缀单元。单元可在输入/输出结束处形成，也可由公共前缀检测或长序列定期间隔截取产生。

文档的 A+B、A+C、A+D 例子表明：前两次请求可以先形成共同的 A 单元，后续才命中 A。缓存构建耗时为秒级，空闲后可能在数小时至数天内清理，并且是尽力而为。固定前缀是必要的设计方向，但不保证第二个请求立即命中，也不保证全部共享文本都已落盘。当前页面没有承诺固定64-token分块，不应按旧说明填充或对齐提示词。

KV 缓存复用输入计算，仍需生成答案。应用结果复用则直接读取已验证答案，可以省掉整次生成，两者必须分别统计。

### Responses API

[官方兼容性表](https://api-docs.deepseek.com/zh-cn/guides/responses_api)明确不支持 `prompt_cache_key`、`prompt_cache_retention`、`previous_response_id`、`conversation` 和 `store`，不支持的请求参数会被静默忽略。上下文缓存由服务端自动管理。

因此，改成 Responses 不是缓存开关，也不能通过 previous_response_id 省去发送历史。若将来为了结构化输出或接口统一而迁移，需独立验证 Pi 适配、输入映射、限额及回执统计，并读取 `input_tokens_details.cached_tokens`；本轮缓存优化不以迁移为前提。

### Pi Agent Core

[Pi Agent Core 官方 README](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)提供固定 systemPrompt、独立 Agent 状态、streamFn、sessionId 和 prepareRequest；[Pi AI 官方 README](https://github.com/earendil-works/pi/blob/main/packages/ai/README.md)描述的缓存参数与会话亲和行为依赖具体 provider/transport。

已同时核对本地安装的两个1.2.0包。本站 `pi-agent.ts` 每任务新建 Agent，使用自定义 ProviderStreams，将预先预留费用的 messages 原样发给 `/chat/completions`，不携带上篇文章；当前没有转发 sessionId/cacheRetention。即使改为转发，也不能据 Pi 的通用选项推断 DeepSeek 支持这些缓存控制。不要为了缓存保留跨文章聊天历史。

本地实现已具备：

- `prompt-layout.ts`：公共编辑规则、场景规则、固定结构在前，动态材料在后；固定文本统一换行。
- `llm.ts`：记录真实 system/user 哈希、模型、输出上限、思考档位、语言；模板队列按模型、场景、system哈希和档位分组。
- `pi-batch.ts`：每批最多8个、并发2、等待20毫秒，仍是逐篇独立请求，不是把8篇拼成一个对话。
- `receipts.ts`：相同有效输入复用 received/completed 回执；并发请求有占用保护，未知付费结果不盲目重发。
- `reports/daily.ts`：最多40个候选，稳定ID排序和摘要限长；内容/参数哈希未变跳过；异步选题与导语前后检查快照，旧任务不得覆盖新版本。

这些应保留。需要改进的是实际前缀的可复用长度和执行节奏，而不是重新添加已有机制。

## 3. 建议按三阶段实施

### 第一阶段：补齐观测与前缀审计，优先做

1. 使用现有真实回执按场景、runtime版本、模型、思考档位、templateHash和输入长度分组。比较同组的命中输入、未命中输入、总输出、原生 reasoning_tokens（有才记）、延迟及有效输出率。原生字段缺失记未知，单列已知覆盖率；结果复用请求排除出原生缓存分母，所有真实收费尝试，包括无效输出的调用，都纳入费用。
2. 对最终发送的 messages 做本地前缀审计，不仅检查模板文件。记录固定前缀哈希/长度、候选数量及内容版本，不记录正文或密钥。不同正文的同场景请求应拥有相同固定前缀；只有ID/时间/计数变化的样本要定位首次差异。字符长度只用于排查，不能冒充 provider token 数。
3. 保持 `公共编辑规则 → 场景规则 → JSON结构/篇幅要求 → 动态材料`。只把各场景确实重复且语义一致的事实、安全和语言规则提到公共区；不把评分专属约束推广到摘要，不加无意义长示例凑缓存。更新公共规则会造成一次冷启动，应集中发布，避免频繁全局改版本。
4. 动态对象统一采用规范字段顺序与稳定序列化，数组按任务语义固定顺序；清除刷新时钟、重试序号等纯运行字段。原文、发布日期、新进展、来源与权限证据必须保留，不能为命中率删除或改写。没有发现相关字段就不做无效改动。

交付验证：最终请求前缀快照测试；同模板不同文章固定前缀一致；文章原文/必要时间仍完整；真实回执可以区分冷样本和后续样本。

### 第二阶段：改进后台任务调度和日报动态前缀

5. 在现有队列上按模板聚合已经到期且通过安全阀的真实后台任务。当前20毫秒窗口很短，不能保证陆续到达的同模板任务聚集。可小范围对比“同模板真实任务连续执行”与原调度；冷模板前几条采用顺序执行，让公共前缀有落盘机会，后续恢复原并发2。缓存冷暖只能根据间隔和实际回执推断，不能假装能读取服务器缓存状态。
6. 不发送空预热/重复问题，不延长每日可调用时段，不提高次数或金额阀。不用固定睡眠承诺缓存建成；给队列设等待上限，首版日报和紧急重试保留优先级，任务轮转避免低频领域饥饿。若延迟增加、命中没有改善，就回退调度实验。
7. 日报现有稳定ID排序解决了相同集合的确定性，但新ID插入前部仍会打断后方所有共享输入。对日内更新，实验保存该期已发送候选的稳定顺序，新候选追加在末尾；同一候选卡片内容不变就保持字节不变。40条上限、必要修订和撤稿仍优先，发生替换就允许缓存失效，不能藏掉变化。模型每次仍看到全部有效候选，原有选题和领域上限保持不变。
8. 分别计算选题和导语的最小有效输入身份。当前全期快照变化后会重走增强流程，但选中条目和顺序相同的导语本来就可通过已有回执复用；继续利用它，只在观察到无谓参数/版本变化时修复身份，不重复新造一个缓存。对选中集合规范顺序的实验须同时固定头条ID和 role，防止图片、条目或阅读重点错配。

交付验证：新候选追加、旧候选修订、撤稿、满40条替换、快照过期、并发占用、正文不变、导语可复用和队列公平性。热点榜继续每五分钟按规则更新，不增加模型调用。

### 第三阶段：仅在证据支持时做任务结构实验

9. 单篇唯一长正文天然难与其他文章共享；不同场景的系统规则先发生分歧时，即使后面是同一篇原文，也不能凭原文相同就共享那一段前缀。因此不要承诺把全站做到90%或100%。
10. 若观测发现同一材料确实被多个兼容任务反复读取，才评估小范围任务族：固定公共规则与该族全部规则/schema在前，同一材料放后，动态任务选择放材料尾部。必须先证明规则不会互相干扰；评分和摘要默认继续独立，不改精选标准，不把长文翻译压成摘要，也不为了复用把所有18个场景塞进一个大提示词。
11. 结合实际输出与 reasoning_tokens，继续收紧评分仅数值、选题仅ID、导语只规定结构和短正文等输入提示词要求。长文翻译按完整度评估，不能以统一短输出上限截断。输出 cap 是安全上限，不是实际生成量；降低 cap 不能替代提示词约束。只有同场景同材料的质量/费用对比显示仍过量，才评估更低思考档位，单独记录变更，避免与缓存收益混算。

这阶段属于后续实验，不是首轮必须执行的重构。

## 3A. 补充核对：Pi 的提示词批处理具体怎样做

用户进一步要求核对 Pi Agent Core 文档的批处理能力，已读取官方 README、`agent.ts`、导出入口，并核对本地1.2.0声明与实现。这里的“批”需要区分：

| 方式 | Pi 的实际语义 | 本站适用范围 |
|---|---|---|
| `agent.prompt(AgentMessage[])` | 一次把多条消息加入同一个Agent上下文，再运行一条Agent循环；不是N个独立任务或N份独立结果 | 同一任务需要多条输入消息时可用；不能当成逐篇隔离的批量评分接口 |
| `followUpMode: 'all'` / `steeringMode: 'all'` | 把该队列选中的消息一起注入后续同一上下文；`one-at-a-time`也是同一会话的逐次消费 | 适合同一事件的连续对话，不适合把不同文章排进去省钱 |
| `toolExecution: 'parallel'` | 并行执行同一模型回合产出的工具调用；某工具要求顺序时整组可顺序执行 | 不是并行运行文章提示词；本站当前编辑Agent `tools: []` |
| 多个独立Agent＋应用队列 | 应用创建独立任务，限制并发，逐一通过streamFn和回执处理 | 本站建议使用；沿用既有TemplateBatcher |
| 一个提示词携带候选列表 | 应用定义批量JSON输出，Pi负责一次普通Agent调用，不自动拆分结果、重试或校验ID | 日报最多40候选的选题已经采用这种业务批处理 |
| 服务商异步Batch API | 本次检查的Core公开接口没有可直接提交独立提示词集合的Batch封装 | 不把Pi批处理等同于服务商批量折扣；是否接服务商Batch另行核验 |

官方入口：[Agent Core README](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)、[Agent 实现](https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent.ts)、[导出入口](https://github.com/earendil-works/pi/blob/main/packages/agent/src/index.ts)。同一Agent正在处理时再次调用prompt会抛错，因此不能对同一个Agent做 `Promise.all(articles.map(a => agent.prompt(a)))`。即便顺序调用，历史也会累积；当前每篇新建Agent的边界应保留。

推荐的本站执行路径：

```text
到期文章任务
  → 检查内容/版本与有效回执
  → 按实际固定模板＋模型＋思考档位分组
  → 每批最多8件，组内按缓存观测选择顺序启动或并发2
  → 每件独立Pi Agent / 独立上下文
  → 原有paidRequest、安全阀与官方DeepSeek调用
  → 各自校验、回执及发布
```

分组调度是本应用负责的工作，Pi负责单件Agent的上下文与调用循环。首批顺序启动只是缓存实验，不是Pi保证的预热模式；不能为凑批等待重要材料，所有到期、过期快照、优先级和公平性约束照常执行。

若目的是“只付一次固定提示词输入费”，需要把多篇材料放在同一个模型请求中；仅并发多个Agent不能达到这个效果。对本站，这会改变每篇独立上下文的约定，因此首轮不做跨文章合并评分。已获允许的日报候选选题可继续在单次请求中批选，使用ID数组并严格验证候选范围、重复ID和重点资格。不能把这种业务候选集合与“多个互不影响的Agent任务”混为一谈。

缓存优化优先靠同模板的真实任务连续调度和稳定公共前缀。有效回执可复用时直接复用，不为了多一个缓存命中数字再发请求。无需为批处理添加一个负责拆任务的收费调度Agent。

## 4. 费用空间与验收

按周表去重后的实际输入量、输出量和单价保持不变，仅把一部分输入 miss 转为 hit：

| 假设输入命中率 | 这批调用可少付 | 总费用下降 |
|---|---:|---:|
| 70% | 1.72元 | 6.48% |
| 75% | 2.60元 | 9.77% |
| 80% | 3.48元 | 13.07% |

公式：`节约 = max(0, 目标命中率 × 总输入 − 已命中输入) × (未命中单价 − 命中单价)`。这些是情景测算，不是可实现率预测，不外推为每月固定节省。全部剩余输入 miss 都变 hit 的纯算术上限为6.98元，但唯一新材料和缓存机制意味着它不可作为工程目标。输出减少10%在同样质量/调用量条件下相当于1.93元，约总费7.24%；不能用漏译、漏事实或无效答案换取。

建议先观察3–7天自然流量，低频场景不足则延长。每个主要模板至少20个可比较的真实付费样本才作初步判断，样本不足直接标记不足；20个也不代表统计显著。按场景/档位/输入长度和时间窗口配对或交替分组，每次只变一种策略；不要额外复制付费请求来凑A/B样本。

通过标准是同类工作实际未命中输入和每件合格情报费用下降，同时事实准确、JSON有效率、精选判断、去重与发布权限保持原验收水平，且队列延迟没有不可接受地增加。总体命中率只作辅助，必须同时看输入总量，防止通过冗长提示词“刷高”比例。

若实施，顺序建议为：**回执分层与前缀审计 → 固定文本/序列化修正 → 同模板自然任务调度小实验 → 日报追加顺序实验 → 再评估跨任务结构**。应用结果复用与篇幅约束贯穿各阶段。继续沿用原测试和预算边界，生产发布另按工作约定确认。
